# technical design

## tech stack

| layer | technology |
|---|---|
| agent integration | claude code / opencode + `skills.sh` |
| mcp protocol | sse / stdio |
| kb server | c++ |
| vector store | faiss (c++, in-memory) |
| embeddings | external api (openai or similar) |
| deployment | docker |

c++ was chosen for two reasons- it's a learning exercise, and faiss is a native c++ library so there's no binding overhead or ffi weirdness.

## architecture overview

![architecture diagram](./assets/Pasted%20image%2020260329085717.png)

the system has three components that talk to each other in a straight line:

```
agent (claude code / opencode)
  ↓ mcp protocol (sse or stdio)
tribal kb mcp server (c++)
  ↓ native c++ calls
faiss vector store (in-memory)
```

the agent calls the mcp server through the skill. the mcp server handles the logic. faiss handles the vector math.

## mcp server

the server implements the mcp protocol and exposes three tools:

### `store_knowledge`

takes a piece of knowledge (text), generates an embedding for it (via an external api call), and stores both the text and the embedding in faiss.

```
input:  { content: string, tags?: string[], source?: string }
output: { id: string, status: "stored" }
```

flow:
1. receive content from agent
2. call embedding api to get vector representation
3. store vector in faiss index
4. store metadata (content, tags, timestamp) alongside the faiss id
5. return confirmation

### `query_knowledge`

takes a natural language question, embeds it, and finds the most similar entries in faiss.

```
input:  { query: string, limit?: number }
output: { results: [{ content: string, score: float, metadata: object }] }
```

flow:
1. receive query from agent
2. call embedding api to get vector for the query
3. search faiss index for nearest neighbors
4. return matched entries with similarity scores

### `list_recent`

returns the most recently stored entries, optionally filtered by tags.

```
input:  { limit?: number, tags?: string[] }
output: { entries: [{ content: string, timestamp: string, tags: string[] }] }
```

## faiss setup

faiss is used in its simplest mode- `IndexFlatL2` for exact l2 distance search. this is fine for the scale this project operates at (hundreds to low thousands of entries). if it needed to scale, you'd swap to `IndexIVFFlat` or `IndexHNSW` for approximate search.

the index lives in memory. on shutdown, it can be serialized to disk using faiss's built-in `write_index` / `read_index` for persistence across restarts.

metadata (the actual text, tags, timestamps) is stored separately in a simple in-memory map keyed by the faiss vector id. this gets serialized alongside the index.

## embedding generation

the server doesn't generate embeddings itself- it calls an external embedding api (openai's `text-embedding-3-small` or similar). this keeps the c++ side focused on mcp protocol handling and vector storage, without needing to bundle a model.

the embedding dimension needs to match the faiss index dimension. for `text-embedding-3-small` that's 1536.

## agent skill

the skill is a shell script (`skills.sh`) that:
1. registers with the agent (claude code, opencode, etc.)
2. starts or connects to the mcp server
3. exposes the server's tools to the agent

for claude code specifically, this means adding the mcp server config so the agent knows about the `store_knowledge`, `query_knowledge`, and `list_recent` tools.

## deployment

everything runs in docker.

```yaml
# docker-compose.yml (conceptual)
services:
  tribal-kb:
    build: .
    ports:
      - "8080:8080"
    environment:
      - EMBEDDING_API_KEY=${EMBEDDING_API_KEY}
      - EMBEDDING_MODEL=text-embedding-3-small
    volumes:
      - kb-data:/data  # for faiss index persistence

volumes:
  kb-data:
```

the container runs the mcp server, which handles both the mcp protocol and the faiss operations. a volume mount handles persistence of the faiss index and metadata between restarts.

## transport

the server supports two transport modes:

- **stdio**: for local usage where the agent spawns the server as a child process. simpler, no networking.
- **sse (server-sent events)**: for remote or shared usage where the server runs as a standalone service. the agent connects over http.

which one to use depends on the deployment- local dev uses stdio, shared team setup uses sse.
