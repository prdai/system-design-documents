## otp token design (round 5)

based on external analysis of the otp flow- the connection key is actually a signed, expiring session token that binds user to org. going with a stateful approach- token has a session id, session data lives in db (user id, org id, expiry, status). on each request we verify signature, look up session, check status. this gives full revocation control. the flow is: user → otp → our api → issue signed token → org uses token → our api verifies → append receipt.
